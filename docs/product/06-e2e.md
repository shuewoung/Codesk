# 6. 端到端加密

出门经中继时，业务内容只在 **Hub ↔ 手机** 两端明文。E2E 主要保手机客户端；局域网直连 Hub 仍明文（本机口令保护）。中继只转发不透明密文。

不要抄 slopus/happy 的同步加密。这里只封管道，不另做密文库、不改业务消息名。

## 目标

| 中继可以看见 | 中继不能看见 |
|---|---|
| `hubId` / `deviceId` / 连接时间 / 报文大小 | 聊天正文、附件、文件路径、命令、Git、审批内容 |
| 信封 `type`（`fwd` / `ping` / `pair`…） | `fwd` 里的应用 JSON |
| 配对码、`deviceToken`、`hubSecret`（管道鉴权） | Hub 内容密钥、设备私钥 |

运营者能数「谁在何时连了哪台 Hub」，不能打开用户在干什么。禁止宣传「连元数据也没有」。

## 密钥

| 密钥 | 谁有 | 存哪 |
|---|---|---|
| Hub 长期 X25519 `hubE2ePriv/Pub` | 仅该台 Hub | `identity.json`（`mode 0600`） |
| 设备 X25519 `devicePriv/Pub` | 仅该手机/浏览器 | Expo：SecureStore；PWA：IndexedDB（WebCrypto / nacl） |
| 内容密钥 `contentKey`（32B） | Hub + 已握手设备 | Hub 明文只在本机；发给设备时用该设备公钥封好 |

同一 Hub 的多台设备共用一把 `contentKey`，所以 `thread_update` / 大附件只加密一次，中继原样广播。吊销设备后 Hub **立刻轮换** `contentKey`，只给还在的设备重封。旧密钥解不开新报文。

算法（三端必须同一套）：

- 握手：X25519 + XSalsa20-Poly1305（nacl `box`，匿名封：临时密钥 + `hubPub`）
- 业务：nacl `secretbox`（XSalsa20-Poly1305），key = `contentKey`
- 编码：nonce 24B、密文均为 unpadded base64url
- 库：Hub 用 Node `tweetnacl`（或等价）；PWA / Expo 同算法，禁止一端 AES-GCM 一端 secretbox

## 配对（公钥不走中继明文）

二维码在电脑屏幕上，摄像头读到，相对中继是带外。

```
https://<中继>/?pair=<code>&hk=<hubE2ePub>
```

- `hk`：Hub 长期公钥，base64url（32 字节）
- 手输码：Hub 的配对页同时显示 `hk` 短指纹（8 个字符，空格分隔）。手输时手机必须再贴/扫 `hk`，只输 6 位码不算完成配对
- 中继的 `POST /api/relay/pair` **只换** `deviceToken`，禁止收发任何密钥

扫完之后、发业务之前：

1. 手机生成 `device` 密钥对，本地收好
2. 手机发信封 `e2e_hello`（不是 `fwd`）。`payload` 是对 `hubPub` 的匿名 box，内层 JSON：`{ v:1, devicePub, deviceId, ts }`
3. Hub 用 `hubE2ePriv` 打开。打不开 → `error.code=e2e_hello_bad`，要求重扫
4. Hub 把当前 `contentKey` + `keyId` 用 `devicePub` box 回去：信封 `e2e_welcome`
5. 手机打开后才允许发 `fwd`

旧设备没有 `hk` / 没有欢迎包：收到 `error.code=e2e_required`，UI 写「请重新扫码配对」。

## 业务报文

信封 `v` 仍是 `1`。有密文时 **不准** 再带明文 `payload`。

```json
{
  "v": 1,
  "type": "fwd",
  "hubId": "...",
  "deviceId": "可选",
  "enc": { "v": 1, "alg": "nacl-secretbox", "kid": "keyId", "n": "<nonce>", "ct": "<密文>" }
}
```

- `ct` 解密后必须是一条完整应用协议 JSON（`send_message` / `thread_update` / `send_approval` …）
- Hub → 多设备：同一 `enc` 广播
- 设备 → Hub：同一 `contentKey` 加密；Hub 不认明文 `payload`
- `kid` 对不上（刚轮换）：Hub 再发一次 `e2e_welcome`；连续失败则 `e2e_required`

明文仍走信封、中继可看：`register_hub` `request_pair_code` `pair_code` `pair` `ping` `pong` `hub_offline` `e2e_hello` `e2e_welcome` `error`。`error.message` 禁止夹带用户文本。

## 中继

- `fwd`：只检查 `enc.ct` 是非空字符串、体积上限；**禁止** `JSON.parse` 解密后的内容，禁止把 `enc` 打进日志
- `e2e_hello` / `e2e_welcome`：当不透明转发，规则同 `fwd`（设备↔该 Hub）
- 现有 `assertFwdPayload`（要求 payload 是应用对象）作废
- 审计照旧：谁、何时、哪个 `hubId`。不记 `ct`
- 局域网直连不经过中继，无 `enc`

## 各窗口

| 窗口 | 做 |
|---|---|
| Hub | 生成/加载 `hubE2e*` 与 `contentKey`；拆 `enc`；回包加 `enc`；吊销时轮换 |
| Web | 中继模式：扫 `hk`、握手、`sendApp`/`onmessage` 加解密；解不开显示「重新配对」 |
| 中继 | 不透明 `enc`；新信封类型；日志无正文 |
| Expo | 同 Web；私钥进 SecureStore |

协议字段先改 `04-protocol.md` 再写代码。

## 验收

- 中继日志、审计、tcpdump 里没有聊天原文、路径、补丁、命令输出
- 改中继源码也只能看到 `enc.ct`，解不开
- 局域网直连行为不变
- 吊销后旧设备即使用旧 `contentKey` 也收不到转发；新报文新 `kid`
- 假 `hk`（中间人换公钥）→ `e2e_hello` 打不开，配对失败，不泄 `contentKey`

## 不做

双棘轮 / 每条消息新密钥、把 `hubId` 也藏起来、加密 `register_hub`、中继存密文历史、局域网 E2E。
